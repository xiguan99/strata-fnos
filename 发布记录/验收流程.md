# strata 出包验收流程（2026-10-29 起，Rain 定的硬要求）

## 什么才算「这个版本做完了」

改完代码、打完包、装进应用中心**都不算完成**。必须做完整回归：

1. **装包**：`trim-cli app uninstall strata --yes` → `trim-cli app install-fpk dist/strata_v<版本>_x86.fpk --yes`
   （`install-fpk` 对已安装应用会报 10236，只能卸载重装；`/vol1/@appdata/strata` 数据目录默认保留。）
2. **目录自检**：`curl -s 'http://127.0.0.1:8791/api/native?refresh=1'` → `catalog.error` 为 null、families 有数、`recommendation` 正常、已装模型的 `missing` 为空。
3. **真实入口加载模型**（必须）：在 8791 页面点「加载模型」，等实例 `ready`。
4. **真发一个请求并检查速度**：走 OpenAI 兼容接口发一条真实对话，要求**有回答**，且速度落在参考区间。
   - 参考基线（RTX 2080 Ti 单卡，IQ3_S，`--kv-resident 16384`、`--max-context 262144`）：**生成 50 T/S 左右、预填充 800 T/S 左右**。
   - 明显低于基线要给出原因（卡被别人占用 / 参数不对 / 换了卡），不能说「能跑就算过」。
5. **贴证据**：`/vol1/@appdata/strata/info.log` 里的角色行（角色表 / 物理设备 / `CUDA_VISIBLE_DEVICES`）+ 引擎启动日志的卡名 + 请求的 token 数与耗时。

只验 `/api/native` 的目录、或只看 manifest 版本号，**不算验收**。

## 不硬编码

用户口径：「一切尽量以网页配置为主，我们尽量不硬编码任何配置项，别人用的环境和我们不一样。」

- 路径、显存预留、KV 常驻、上下文长度、GPU 序号一律走网页设置页，代码只留合理默认值与探测。
- 现有写死项清单见 `发布记录/硬编码配置清单.md`，按其中的待办逐步搬进设置页。
- 每次改动都要问一遍：这台机器的哪个特征被我写进代码了？别人装上会不会错？

## 出包护栏（已加在 `scripts/build.sh`）

- 出包前类完整性自检：`class Strata` 必须仍有 `hardware/configs/read_config/model_paths/install_job/tracked_server`，否则不许出包（0.2.7.5 就是类体被截断导致界面报「未报告受支持的显卡」）。
- 同名版本不许覆盖：`dist/strata_v<版本>_x86.fpk` 已存在则构建失败；开发期确需覆盖设 `STRATA_ALLOW_REBUILD=1`。
- 补丁守卫：局域网 Origin（`isLocalOrigin`）、卡名日志（`def log_card_note`）、角色映射（`function rolesToDevices`）三处缺一不可。

## 发布

- 包不入 git（`dist/*.fpk` 在 `.gitignore`），引擎二进制也不入 git（`fnpack/app/engine-bundle/.gitignore` 只放行 `*.json`/`*.txt` 元数据）。
- 打 tag `v<版本>`，push 分支与 tag，再在 GitHub 建 Release 并上传 fpk 资产（应用中心的更新检查认 Release 资产）。
- push 必须走 `http://127.0.0.1:10809` 代理；单个请求超过约 600 s 会 408，所以大二进制不要进 git。
- **推送的 commit 必须与 tag 和 Release 资产同属一个版本**：`ghmain` 推的那个 commit，其 `VERSION` 必须等于 tag 的版本号、等于 Release 里 fpk 的版本号，三者互相对上再回报。
- **VERSION 已经 bump、但包还没出的 commit 不许推 `ghmain`**（2026-11-01 定）。例：`21864720` 是 0.2.9.1（VERSION=0.2.9.1，包已出）；紧接着的 `56dca7bc` 把 VERSION 改成 0.2.9.2 但没出包，它只能留在本地，等 0.2.9.2 真出包、验收完再推。否则会出现「ghmain 是 0.2.9.2、tag 是 v0.2.9.1、Release 是 0.2.9.1」这种三数错位——上次就是这么出的错。

## 加载验收：一律先看 info.log 有没有降级行（2026-11-01 起）

- 2026-11-01 实测：可用内存低于引擎 arena 时（本次 44 GB < 46 GB），引擎按 `STRATA_ARENA_RAM_WAIT_S`（默认 20 s）逐 5 s 打点等满后判 RAM 不足，**control 会自动降级重试**并以「低内存模式」起来（43 GB 留 RAM、其余从 SSD 读），job 最终是 `done / ready` —— 不报错、不 failed。
- 代价是硬的：同机 8K 预填充 497.4 T/s（正常 976.2，−49%）、TTFT 16.0 s（正常 8.2 s）。「ready 但只有一半速度」比 error 更难查。
- 所以每次 load 成功都要在 `/vol1/@appdata/strata/info.log` 里核一行：
  `[fnOS] load ok after Ns: <模型> on GPU <卡>, port <端口>, full memory mode | LOW-MEMORY mode (...)`（0.2.9.2 起写入）。
- **带 `LOW-MEMORY mode` 的实例一律不算达标实例**：不拿它做性能验收、不进基线、不写进发布记录的性能数字；先腾内存重载到 `full memory mode` 再测。
- 若 info.log 里既没有 `load ok` 也没有 `load failed`，说明这次 load 没走真实入口（外部起的引擎），同样不能当达标实例。
