# 0.2.9.1 解码掉一半：现场判定与修法

时间：2026-11-01 22:05–22:20　被测实例：pid 1815952（引擎 0.1.55，21:13:52 启动，app 0.2.9.1，GPU1/2，swift-iq3_s）

## 一、判定结论（先给答案）

**既不是「RAM/swap 正在换页」，也不是「显存装不下专家」。主因是宿主机 CPU / 内存带宽侧的争抢：**
引擎自己 29 个 pool worker 在整机持续自旋（空闲时也烧 28.6 核）+ 每请求 6 个 checkpoint / 6.96 GB 对话缓存的拷贝 + 36.9 GB 的 KV 从 pinned RAM 回放，把 host 相位（CPU 专家计算段）从 3.5 ms 拖到 13–116 ms/窗口；GPU 只跑 42–54% util，是在等 CPU，不是 GPU 变慢。
**RAM 紧（RSS 62.4 GB / MemAvailable 17 GB）是放大器，不是当下致因**——实测零换入、零主缺页。

### 逐条否证/确认（都是实测数字）

| 假说 | 判定 | 证据 |
|---|---|---|
| 显存装不下专家、频繁走 PCIe | **否定** | expert cache 命中 **98.4%**（10,829,435/11,009,543），PCIe 的 GPU 读取只 **0.1%**，VRAM hits 28.12 条/layer-window；慢窗口的 `CPU experts` 反而更低（0.43 vs 快窗口 0.25–4.11），swaps/window 也更低（3.2 vs 曾 24.0） |
| 内存不够 → 专家页被换出 → 换入 | **否定（当下）** | 生成进行中 5 s 采样：`majflt 0.0/s`、`pswpout 0/s`、`pswpin 3/s`（≈0）、引擎磁盘读 0.7–1.3 MB/s、`/proc/pressure/{cpu,memory,io}` 全 **0.00**。VmSwap 1.80 GB 是历史残留（pswpout 累计 3003 万页） |
| CPU 侧被拖慢 / 内存带宽被抢 | **成立** | `per-layer host` 3.48 → **21.31**（最坏 116.30）ms，而 `GPU-reach wait` 全程稳定 12.4–16.9 ms；`CPU 30.75 ms/window` 但 CPU 专家只有 0.43 条 → CPU 时间花在别处；引擎**空闲时 30 线程合计烧 2860% CPU（28.6 核）**，线程名 `strata-pool-*`，`voluntary_ctxt_switches` 平均仅 25538（约 7 次/s）→ 纯自旋不是阻塞；生成期 GPU1/2 util 只有 54%/46% |
| GPU 频率/功耗墙 | 否定 | GPU1/2 均 P2、SM **1950/1890 MHz**、mem 6800 MHz、151/134 W（限 180 W，SW power cap 生效但频率没掉） |

补充量化：
- 单线程 memcpy（256 MiB）**2.14 GB/s 拷贝 / 4.28 GB/s 读写**。本机 2×Xeon E5-2697 v4（每路 18C/36T、4 通道 DDR4），这个数明显偏低，说明内存带宽已被并发拷贝/自旋吃掉一大块。
- 每个请求前都有 `conversation cache: parked …`：`110393 tokens in 4976.1 ms; parked=3 bytes=6955847456 evictions=4 snapshot_bytes=2517714688`；更早 `84211 tokens in 8067.5 ms`、`107787 in 1952 ms`、`72570 in 5557 ms` → 每次切对话要拷 5.8–7.0 GB。
- 每请求 `6 checkpoints`（`--prompt-cache` 默认 6，每个约 118 MB）。
- `KV streaming: 96.34% of 250408206 block reads hit VRAM, 36905.5 MiB read from RAM`（累计），随对话变长单调增长。
- 配置现状：`--max-context 262144`、`--kv-resident 20480`、`--batch 2`、`--spec 4`、`--pool-workers 29`、`--aux-cpus auto`、`--host-core last`；九项并行栈全开（`STRATA_CKPT_POOL=1 … QSA_SLOTS=1`）；`STRATA_POOL_SPIN_US` 未设（走自旋默认）。

## 二、修法（按风险从低到高，每项只改一项，需你点头后 A/B）

| # | 改什么 | 预期收益 | 风险 |
|---|---|---|---|
| F1 | `--conversation-cache-mib 2048`、`--conversation-cache-slots 2`、`--prompt-cache 2` | park 峰值从 6.96 GB/5 s 降到约 2 GB/1.5 s，解码期拷贝与带宽抢占明显减少；checkpoint 从 6 降到 2 | 低。代价：来回切长对话时 KV 重建多花几秒 |
| F2 | `--pool-workers 8`（必要时加 env `STRATA_POOL_SPIN_US=0`） | 释放约 20 个核给 host 相位与拷贝，自旋 CPU 从 28.6 核降到个位数 | 中。CPU 专家吞吐可能下降——但实测 cex 只有 0.43 条/层，影响应很小 |
| F3 | `--kv-resident 8192`（或把 `--max-context` 256K 降 192K） | 减少 pinned RAM 里的 KV 与 36.9 GB 级回放 | 高。直接削长上下文能力，要用户拍板 |
| F4 | 视频平台 06 批与 strata 错峰（jasna 现占 155% CPU） | 少一路 CPU 争抢 | 跨团队，需协调 |

**A/B 口径**（每项 3 次冷态取中位）：同一 prompt（约 91 k 上下文）、8K 预填充 + 512 解码；记录 decode tok/s、`per-layer host`/`CPU`、expert 命中、loadavg、GPU util。改动只走设置页参数（不重装、不出包、不改界面）。

## 三、面板那两个「异常」怎么读

1. **「此请求的预填充 9 t/s」是摊平值，不代表预填充能力。**
   原始行：`prompt 58867 = 58716 reused + 151 read in 15900 ms (9.5 tok/s)`。分子只有新增的 **151** 个 token，分母 15.9 s 还包含 6.5 GB 对话缓存 park/restore 的固定开销。复用的 58716 token 不参与预填充计算。同日同机正常预填充是 **302.9 / 842.6 / 947.8 tok/s**。读法：`read in X ms (Y tok/s)` 的 Y 只在新 token 多时有意义；新 token 很少时看总耗时里是否夹了 park/restore。界面按用户要求不动。
2. **「传输至所选GPU的总量（PCIe）不可用」不是驱动不支持。**
   这组 GPU 传输/请求统计由 control 的 monitor feed 供数（`api_monitor`，默认关，历史内存 deque 100 条），关着时这一格取不到计数器；打开后才有数。开它属设置项，等你点头。

## 四、两条可疑项的判定

- `--max-context 262144` 与设置页 `ctx.length` 128K 不一致：这是两个字段，引擎侧实际按 **256K** 跑（args 里写的就是 262144），设置页显示的值是另一处/旧值。内存因此按 256K 预留，是 RSS 62 GB 的一部分来源。属显示层不一致，**不改界面**，记录待报。
- 对话缓存 6.5 GB + 62 GB RSS 顶到 swap：部分是历史真换出（VmSwap 1.8 GB），但**当前无活跃换页**；它的实际危害是让 page cache 只剩 0.5 GB，任何回读都会变慢。

## 九、unload 返 400 的根因（2026-11-01 23:56 实测抓到响应体）

**现象**：`POST /api/native/instances/9b13ce69…/unload` → HTTP 400，响应体
`{"error":"server_stop_deadline_expired","code":"control_failed"}`；
但 8 秒后 GPU1/GPU2 已从 20740/21058 MiB 回到 **1 MiB**（引擎实际被杀了），`MemAvailable` 19.4 → 25.2 GB，实例却停在 `status: error`；**再调一次 unload → 200，`instances []`**。

**调用链（源码级）**
1. host 起引擎时传的 drain 预算很小：`fnpack/app/host/server/control-runtime.mjs:292` `async start(name,{waitSeconds=300, dieWithPid=process.pid, drainSeconds=15})` → `['runtime','start','--profile',name,'--wait',…,'--shutdown-timeout',String(drainSeconds)]`，即 **shutdown-timeout = 15 s**（control CLI 自己默认 30 s）。
2. control 停止子进程：`upstream/xc55/strata_control/runtime.py:998 _stop_child()` —— SIGTERM 后 `child.wait(timeout=self.shutdown_timeout+8)` = **23 s**；超时则 `_kill_child_tree()` + 再等 10 s，然后 `return {"ok":False,"state":"failed","error":"server_stop_deadline_expired","exit_code":8}`（`:1010`）。
3. host `control-runtime.mjs:314 async stop(name,{waitSeconds=120})` 把 `ok:false` 当失败抛出 → `native-control.mjs:206 async function unload(id,force=false)` 第四个出口把实例置 `status='error'` → 路由 `index.mjs:1087-1088` 统一 400 `code: control_failed`。

**为什么 23 s 不够**：本机实例是 46.84 GiB arena + 20.48 GiB KV resident + 16.21 GiB 专家缓存，SIGTERM 后的收尾（munmap/flush/写 ready 文件删除/pipe 关闭）本身就超过 23 s。**不是卸载失败，是「已杀干净但时钟先到」，被报成失败。**

**修法（下一版 host 补丁，二选一或都做）**
- 把 `drainSeconds` 从 15 提到 60（一行常量），让正常收尾走完；
- 在 `unload()` 里把 `server_stop_deadline_expired` 视为**成功**：此时引擎树已被 kill、端口已释放，判 `stopped` 而不是 `error`（否则用户看到红色 error 却实际已停）。

## 十、端口 18500 → 18501 的原因（无害）

`fnpack/app/host/server/native-control.mjs:475` `cfg.port = await freePort(args.port)`；
`:562 async function freePort(requested)` —— 从 `requested ?? 18500` 起扫到 **+20**，跳过「已知实例已占用」的端口，再对每个候选做 `net.createServer().listen(port,'127.0.0.1')` 探测；被占就下一个，显式指定且被占才报错。

### 12.2 判定：**THP 碎片假设成立**

决定性证据是 `per-layer host`：**470 ms → 5 ms**（CPU 分量 469.78 → 9.75 ms）。这个量级不是"略慢"，是 TLB 崩掉之后每层遍历 51 GiB 匿名内存时页表走不完的典型形状——4 KiB 页占 86% 时，同样一次遍历要翻 20–50 倍的 TLB miss。**91K prefill 4.3 倍（394 → 1660.9）是结果，不是原因。**

但有一条必须修正原来的判据：**大页只回到 60.1% 就已经全速了，80% 的门槛偏保守。**

| 原判据 | 条件 | 实测 | 结论 |
|---|---|---|---|
| A 碎裂假设成立 | 占比 ≥80% 且 8k ≥900/70、91k ≥600 | 占比 60.1%；8k 982.7/66.9（非空载）；91k 1660.9 | 速度达标、占比未达标 |
| B 占比上去速度没回 | 占比 ≥80% 但速度 200 级 | 速度已到 982/1661 | ❌ |
| C 重启无效 | 占比 ≤25% | 60.1% | ❌ |

⇒ **验收门槛改为可操作口径：`AnonHugePages 占匿名内存 >50%` 且 `per-layer host <20 ms`。** 不再用 80%——本机 `vm.nr_hugepages=0`、`MAP_HUGETLB unavailable`，大页全靠 THP 现分配、回退率长期 36%，80% 在这个环境下永远达不到，写进验收等于永远判失败。

### 12.4 结论与运维建议

**结论：不用出包，不用改任何 flag。整机重启即恢复满速。**

运维建议（已并入 §11.4 验收流程）：

1. **跑大上下文（≥64k）前先看两项**：引擎 `AnonHugePages` 占匿名内存比例（**<50% 就别指望满速**）、机器 uptime（>2 天要警惕）。
2. **性能掉了先重启，别先改参数**——本次实测重启后 load 161 s / arena 1.46 GiB/s / 8k 982.7 / 91k 1660.9，全部回到快实例档。
3. 若用户不想重启，次优方案是 `sync; echo 3 > /proc/sys/vm/drop_caches` + `compact_memory`（未实测，仅候选，下次掉速时验证）。

### 12.5 `thp_fault_fallback` 稳态观察口径（Rain 2026-11-02 要求）
